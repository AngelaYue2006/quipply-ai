# Changelog

## V1 dark theme and job-board scrolling (2026-11-01)

- Switched the full frontend to a dark ink palette with lilac actions, muted colored accents, and softer asymmetric shapes. Forms, badges, notices, profile sections, resume review, and job details use the same dark palette; native controls use dark color-scheme.
- Removed the job list's nested vertical scrollbar. Virtualization now tracks the whole Jobs page, with a measured list offset that updates when filters expand or the viewport changes. The page heading and filters scroll away so the list can occupy the viewport.
- Retained horizontal scrolling for wide job columns and reduced-motion support. No dependencies added.

## V1 frontend redesign (2026-11-01)

- Rebuilt the dashboard shell with desktop sidebar, mobile navigation, slate/teal styling, shared form controls, and visible keyboard focus. No new dependencies or decorative gradients.
- Redesigned the job board with summary counts, status tabs, readable opportunity rows, grouped advanced filters, keyboard-accessible sorting, and actionable empty states.
- Replaced fixed minimum-score presets with a numeric 0?100 input. Blank includes all scores; 0 filters to jobs with a numeric score. Posting age and the default pull window now accept custom day counts.
- Added profile section shortcuts, completion indicators, consistent settings and resume-review layouts, and a responsive job detail dialog with focus containment, Escape dismissal, and notes-save feedback.
- Cleared selection when filters change; bulk actions capture the IDs of visible selected jobs. Profile edits and imports now invalidate cached job scores.
- Verification: TypeScript and frontend/filter-test ESLint checks pass; all 105 tests pass, including four new filter tests. Production build passes with existing Vite config-loader and bundle-size warnings.
- Browser visual verification remains incomplete: browser connector unavailable; native Chrome inspection timed out awaiting Computer Use approval. No live job pulls or model requests were made for QA.

## 0.1.0 — V1 MVP (2026-11-01)

Built the core loop from SPEC.md plus resume import: profile → pull jobs → fetch description → score match.

### Included

- **Skeleton (M0):** pnpm, TypeScript strict, ESLint (bans importing the Anthropic SDK outside `src/llm/`), Vitest, Fastify on 127.0.0.1 with Host/Origin checks and a per-install token on every API call, React + Vite + Tailwind dashboard, Drizzle schema and first migration for all eight tables, `src/llm/structured()` with Zod validation, one repair retry, and logging of every call to `llm_calls` with tokens and cost.
- **Profile (M1):** every section in the spec, each with its own Save; list editing; completeness meter; export/import JSON; resume upload, default resume, plain-text extraction (no model).
- **Resume import (M2):** PDF sent to Claude as a document block; the draft schema contains only identity, contact, links, education, experience, projects and skills; field-by-field review (new fields checked, changed fields unchecked); Accept selected / Discard.
- **Job board (M3):** `JobSource` interface + Simplify internships source with ETag; Pull jobs with a 3/7/14/30/all window; upsert, closed detection, counts; filters (text, category, term, location, remote, ATS, posted within, degree, status, min score, "Apply my preferences", show closed), sorting, New badge, statuses, notes, bulk status; virtualized table.
- **Descriptions (M4, single job):** Greenhouse, Lever and Ashby public APIs, Readability for everything else, `needs_browser` error with a paste box; one request at a time, ≥1 s apart, clear user agent.
- **Matching (M5, single job):** six eligibility rules in code with phrase-list tests, `match-fit@1` prompt (verbatim from the spec), quote check, score and verdict in code, stale detection on profile or matcher version change, match panel and score column. `pnpm match:demo` prints the prompt, input, raw model JSON and result.

### Deferred (not in this MVP)

- Score selected (bulk scoring with cost estimate), bulk description fetch.
- `match:eval` and the 20 hand-labeled jobs, so the "14 of 20" acceptance check hasn't been run.
- SQLite FTS5 search; text search covers company and title only.

### Decisions that differ from the spec

- The app lives at the repo root, not in `apply-engine/`.
- UI components are small hand-written Tailwind components in the shadcn style, not generated by the shadcn CLI.
- `unpdf` extracts resume text (the spec allowed "a library such as pdf-parse").
- `job_pulls` has three extra columns: `malformed`, `not_modified`, `window_days` (needed for counts and the widened-window rule).
- Stored postings that disappear from the listings file are marked closed, like ones that turn inactive.
- Resume import uses `claude-opus-5-5` with the server-side refusal fallback (`fallbacks: "default"`); matching uses `claude-haiku-5-5`. Both are set in `.env` or on the Settings screen.

### Verified external details (2026-11-01)

- Listings URL from the spec works: 13.1 MB, 17,476 entries, 5,119 `active && is_visible`; served with an ETag; 304 on repeat. All listed fields are present. `date_posted` is Unix seconds. 7-day window: 587 postings.
- Listing values: degrees use `Bachelor's`, `Master's`, `PhD`, `MBA`, `Associate's`…; sponsorship values are `Other` (5,099), `Does Not Offer Sponsorship`, `U.S. Citizenship is Required`, `Offers Sponsorship`; terms include `N/A`.
- Greenhouse: `boards-api.greenhouse.io/v1/boards/<board>/jobs/<id>` returns entity-escaped HTML in `content`. EU boards (`*.eu.greenhouse.io`) have no reachable API host, so they fall back to Readability.
- Lever: `api.lever.co/v0/postings/<company>/<id>` returns `description`, `lists[]`, `additional`.
- Ashby: `api.ashbyhq.com/posting-api/job-board/<board>` returns all jobs with `descriptionHtml`/`descriptionPlain`; the job is found by id.
- Live check: 3 Greenhouse, 3 Lever and 3 Ashby descriptions fetched; Workday and custom career pages returned `needs_browser` as expected.
- Anthropic TS SDK 1.3.0: structured outputs via `output_config.format` with `zodOutputFormat`; PDFs as base64 `document` blocks; prices from the current model table ($0.10/$0.50 per M tokens for Haiku 5.5, $4/$20 for Opus 5.5).
- A live `match:demo` run reached the API but the key in `.env` was rejected (401), so no live model output has been checked yet.
